## Sécurité applicative

Une application est un programme (ou un ensemble de programmes) qui traduit des instructions fournies par l'utilisateur en actions effectuées par le système. Toute application peut contenir des failles de sécurité qui pourraient être exploitées par un utilisateur malveillant. De telles failles peuvent se trouver à plusieurs endroits:
- Dans le **code source** du programme
- Dans sa manière de **stocker** l'information (par exemple, dans une base de données)
- Dans sa manière de **communiquer** l'information à un autre système

Pour trouver des failles à exploiter, un utilisateur malveillant a plusieurs techniques à sa disposition. Nous allons en explorer quelques unes.


## L'ingénierie inverse

Supposons que le hacker est en contact avec un fichier exécutable. Habituellement, un programme exécutable est compilé en code machine et donc très difficile à lire par un humain, mais ce n'est pas toujours le cas. On peut retrouver trois grandes catégories de fichiers exécutables:

- **Code machine (natif)**: Les langages comme C, C++, Delphi, Rust et Go sont dotés de compilateurs dits "natifs" ou "ahead-of-time", qui produisent du code machine directement exécutable par le processeur. Le code compilé est spécifique à une architecture précise de processeur (comme x86-64 ou arm64) ainsi qu'à un système d'exploitation (Windows, Linux...) et donc n'est pas portable.
- **Code intermédiaire (bytecode)**: Les langages comme C#, VB.NET ou Java ne sont pas compilés en code machine. À la place, ils sont compilé en langage intermédiaire (C# et VB.NET sont compilés en MSIL pour CLR, Java est compilé en bytecode Java pour la JVM). Pour permettre une portabilité, ce code est traité à l'exécution par un procédé nommé "compilation Just-In-Time (JIT)", et c'est le framework logiciel qui se charge de traduire ce code en instructions pour le processeur.
- **Code interprété (script)**: Finalement, des langages comme JavaScript, PowerShell et bash ne sont pas compilés. Le fichier exécutable est en fait un fichier texte qui, lorsque passé dans un interpréteur, est traduit en instructions pour le système.

L'ingénierie inverse, ou rétro-ingénierie, c'est l'art de partir du programme exécutable et d'en comprendre le fonctionnement, c'est-à-dire en lisant le code source. Dépendant du type d'exécutable, ce procédé peut être assez difficile.

Les programmes compilés natifs sont les plus difficiles à en déduire le code source, car celui-ci est perdu. En décompilant (ou en désassemblant) du code natif au moyen d'outils spécialisés comme [IDA Pro](https://hex-rays.com/ida-pro), [Ghidra](https://github.com/NationalSecurityAgency/ghidra) et [Cutter](https://cutter.re/), on obtient des instructions de bas niveau, qu'on peut traduire en langage d'assemblage (appelé Assembleur ou ASM), qui est très difficile à comprendre ([Voici un exemple de "Hello World" programmé en assembleur](https://github.com/nukethebees/github_io/tree/main/hello_world_win_asm)). Des outils comme Ghidra et IDA Pro peuvent aussi reconstruire un pseudo-code en C. Ce code est souvent assez lisible pour comprendre la logique d'un programme, mais les noms de variables et de fonctions d'origine sont perdus, ce qui demande beaucoup plus d'efforts que pour du code intermédiaire.

Les programmes compilés en code intermédiaire, bien qu'ils soient souvent des .exe, contiennent du bytecode accompagné de nombreuses métadonnées (noms des classes, des méthodes, des variables...). Un logiciel de décompilation peut donc généralement reconstruire un code source très proche de l'original. Les applications .NET (programmées en C# ou en VB.NET) peuvent être décompilées en utilisant des logiciels comme [JetBrains dotPeek](https://www.jetbrains.com/decompiler/) ou [ILSpy (opensource)](https://github.com/icsharpcode/ILSpy). Des produits semblables existent pour Java, comme [Java Decompiler](https://java-decompiler.github.io/).

Les programmes interprétés, quant à eux, ne sont pas compilés donc on peut consulter leur code source directement au moyen d'un éditeur de texte.


## Outils de décompilation

### Analyser avec un éditeur de texte

Premièrement, vous pouvez essayer d'ouvrir le fichier exe dans un éditeur de texte (comme le bloc-notes) pour en reconnaître les chaînes de caractères. À travers tout ce charabia, pouvez-vous reconnaître du texte lisible? Chercher le code là-dedans est un peu comme chercher une aiguille dans une botte de foin, mais vous pouvez au moins obtenir des indices que ce code est compilé en .NET pour CLR. En trouvez-vous?


### Ressortir les chaînes de caractères

L'outil [Strings](https://learn.microsoft.com/fr-ca/sysinternals/downloads/strings) permet de sortir toutes les chaînes de caractères lisibles (ASCII et Unicode). Téléchargez l'outil et sauvegardez-le dans un répertoire sur votre ordinateur (vous aurez besoin de l'extraire du fichier Zip). 

Pour lancer l'outil, vous ne pouvez pas simplement double-cliquer dessus puisqu'il s'agit d'un outil en ligne de commande. Démarrez un terminal (cmd ou PowerShell) et déplacez-vous dans le répertoire où se trouve l'outil. Puis lancez l'outil avec la syntaxe suivante:

```
.\strings.exe -n 8 "chemin\vers\monSecret.exe" > .\strings.txt
```

L'argument `-n 8` indique qu'on veut extraire les chaînes de 8 caractères et plus. Le chemin doit pointer vers le fichier exécutable à analyser. Finalement, `> .\strings.txt` permet de dévier la sortie vers un fichier texte plutôt que dans la console.

:::tip
Voici un autre outil intéressant: [MiTeC EXE Explorer](https://www.mitec.cz/wp/mee/). Il permet d'obtenir une foule d'informations techniques sur un fichier exécutable. Un de ses onglets permet de lister les chaînes de caractères affichables, comme Strings mais en interface graphique. Par contre, on ne peut pas spécifier un nombre de caractères. On peut aussi explorer les ressources incluses dans le fichier. Bref, c'est intéressant à essayer. Notez que cet outil n'est gratuit que pour un usage personnel, éducatif et non commercial.

![MiTeC EXE Explorer](../assets/exeexplorer.png)
:::


### Décompiler l'application

Sans nécessairement trouver toute l'information à l'aide des outils précédents, nous avons pu déterminer qu'il s'agit d'une application .NET. Il y a donc du code intermédiaire. Nous pouvons tenter de décompiler le programme afin de lire le code source en C#. 

On va utiliser **dotPeek** de JetBrains pour décompiler l'application:
- Au cégep, démarrez le logiciel JetBrains Toolbox à partir du menu Démarrer et installez DotPeek
- À la maison, [suivez ce lien](https://www.jetbrains.com/decompiler/download/?section=offline-installer) pour télécharger et installer DotPeek.

:::tip
Il existe d'autres logiciels de décompilation DotNet. Le préféré de Vincent est [ILSpy](https://github.com/icsharpcode/ILSpy). Son mode de fonctionnement est sensiblement le même.
:::


## L'ingénierie inverse à l'ère de l'IA

Tout ce qu'on vient de voir repose sur une hypothèse: lire du code décompilé (surtout du code natif) demande beaucoup de temps et d'expertise. Cette hypothèse est en train de tomber. Depuis 2025-2026, les grands modèles de langage (LLM) sont devenus assez bons pour lire du pseudo-code, renommer les variables et les fonctions, deviner l'intention du code et même le réécrire dans un autre langage.

### Des agents branchés sur les décompilateurs

Des projets open source comme [GhidraMCP](https://github.com/LaurieWired/GhidraMCP) et [IDA Pro MCP](https://github.com/mrexodia/ida-pro-mcp) permettent de brancher un agent IA (Claude, ChatGPT, Copilot...) directement sur Ghidra ou IDA Pro. L'agent peut alors naviguer dans le binaire, décompiler des fonctions, les renommer, ajouter des commentaires et poser des hypothèses, le tout sans intervention humaine. On parle parfois de *vibe reversing*.

Le travail qui prenait des semaines à un expert peut maintenant être lancé le soir et regardé le lendemain matin.

### Quelques exemples récents

- **Ports de jeux vidéo (automne 2026)**: En quelques semaines, des centaines de projets ont été publiés où des jeux commerciaux (Halo, GTA: Vice City, The Simpsons: Hit & Run...) ont été décompilés à l'aide d'IA, puis portés pour tourner dans un navigateur web ou sur d'autres plateformes. Plusieurs fonctionnent étonnamment bien ([Kotaku](https://kotaku.com/we-might-be-cooked-as-these-vibe-coded-web-browser-ports-of-halo-the-simpsons-hit-and-run-and-gta-vice-city-seem-to-work-perfectly-2000743300), [PC Gamer](https://www.pcgamer.com/gaming-industry/pc-ports-of-old-console-games-are-the-new-ai-vibe-coding-battleground/)).
- **Reproduire un produit à partir de son comportement (février 2026)**: Un ingénieur de Cloudflare a réimplémenté la majeure partie de l'API du framework Next.js en environ une semaine, en dirigeant un agent IA et en se servant de la documentation et des tests comme spécification ([vinext](https://blog.cloudflare.com/vinext)). Il n'y a pas eu de décompilation ici, mais le principe est le même: on reproduit un logiciel en observant ce qu'il fait.
- **Réécrire pour changer la licence (mars 2026)**: Le mainteneur de la librairie Python *chardet* l'a réécrite au complet avec Claude Code et l'a republiée sous licence MIT plutôt que LGPL. L'auteur original conteste: selon lui, ce n'est pas une réécriture « en salle blanche » (*clean room*) puisque l'IA et le mainteneur connaissaient déjà le code original ([LWN](https://lwn.net/Articles/1061465/), [The Register](https://www.theregister.com/2026/03/06/ai_kills_software_licensing/)). Le débat n'est pas réglé.

### Les limites

L'IA n'est pas magique. Les études récentes montrent que le code produit par les LLM est plus *lisible* que celui de Ghidra ou IDA, mais il est moins souvent *correct*: l'IA peut halluciner des fonctions, simplifier une logique subtile ou même faire disparaître une vulnérabilité présente dans le binaire original. Pour un port de jeu, ce n'est pas grave. Pour une analyse de sécurité, il faut toujours vérifier ce que l'IA affirme en retournant au code désassemblé.

### Qu'est-ce que ça change pour la sécurité?

- **La sécurité par l'obscurité est encore plus faible qu'avant**: Compiler en natif, obfusquer les chaînes de caractères ou cacher la logique dans une DLL ne fait que ralentir un attaquant. Avec l'IA, ce ralentissement est beaucoup plus court.
- **Un secret dans un exécutable n'est pas un secret**: Clés d'API, mots de passe, chaînes de connexion, algorithmes de licence... Tout ce qui est livré au client doit être considéré comme public. La vraie protection doit se faire côté serveur.
- **Les défenseurs en profitent aussi**: Les mêmes outils permettent d'analyser un logiciel malveillant beaucoup plus rapidement, d'auditer une librairie sans code source ou de retrouver une faille dans un vieux binaire dont le code a été perdu.
- **Les questions légales et éthiques deviennent plus pressantes**: Au Canada, la *Loi sur le droit d'auteur* prévoit certaines exceptions pour l'ingénierie inverse (notamment pour l'interopérabilité et la recherche en sécurité), mais redistribuer un jeu ou un logiciel reproduit à partir d'un produit commercial reste une autre histoire. Le fait qu'une IA ait fait le travail ne donne aucun droit supplémentaire.

:::info Discussion
- Si n'importe qui peut décompiler et reproduire votre application en une nuit, qu'est-ce qui protège encore votre entreprise?
- Est-ce qu'une réécriture faite par une IA qui a « lu » le code original peut être considérée comme une œuvre nouvelle?
- Dans le TP3, quelles informations de l'application ne devraient tout simplement jamais se retrouver dans le .exe?
:::

## 🚩 Défis CTF - Décompilation

Les exercices suivants sont des défis de type CTF (Capture The Flag). Vous devez analyser les applications pour trouver les secrets cachés et comprendre leur fonctionnement.

### CTF-decomp (1 point)

📄 **Fichier de remise**: `ctf-decomp.md`

**Objectif**: Trouver la phrase secrète cachée dans l'exécutable.

1. Téléchargez l'application [CTF-decomp.exe](https://github.com/departement-info-cem/3s4-cybersec/releases/latest/download/CTF-decomp.exe)
2. Lancez l'application - elle vous demande d'entrer un secret
3. Utilisez un décompilateur .NET (dotPeek, ILSpy, [dnSpyEx](https://github.com/dnSpyEx/dnSpy)) pour analyser le code
4. Trouvez la phrase secrète et entrez-la dans l'application pour valider

:::info Indice
La phrase secrète est stockée quelque part dans le code... Les développeurs font souvent l'erreur de mettre des secrets directement dans leur code source!
:::

**Récompense**: 1 point au tableau des scores si vous trouvez le secret.

---

### CTF-ecrit-partout (3 points)

📄 **Fichier de remise**: `ctf-ecrit-partout.md`

**Objectif**: Cette application de prise de notes semble innocente, mais elle cache vos données dans des endroits surprenants. Trouvez TOUS les emplacements où vos notes sont stockées!

1. Téléchargez l'application [CTF-ecrit-partout.exe](https://github.com/departement-info-cem/3s4-cybersec/releases/latest/download/CTF-ecrit-partout.exe)
2. Lancez l'application et créez quelques notes
3. Utilisez la fonction "Supprimer toutes les notes"
4. **Question**: Vos notes sont-elles vraiment supprimées? 🤔

**Votre mission**:
- Décompilez l'application pour comprendre où elle stocke les données
- Attention: les noms de fichiers sont **obfusqués** dans le code (ASCII, hex, opérations sur caractères)
- Trouvez les **3 emplacements** où les notes sont écrites:
  1. Un fichier avec un chemin **relatif** qui remonte dans l'arborescence
  2. Un fichier dans le **profil utilisateur**
  3. Un fichier avec un chemin **absolu** Windows

:::warning Attention
Même après avoir "supprimé" vos notes via l'interface, certains fichiers peuvent rester sur votre disque! C'est un problème de confidentialité important.
:::

**Récompense**: 
- 1 point par emplacement trouvé (3 points maximum)
- Bonus: Expliquez comment les noms de fichiers sont obfusqués dans le code

:::tip Outils utiles
- Process Monitor pour surveiller les accès fichiers en temps réel
- Un décompilateur .NET pour lire le code source
- La commande `dir` ou l'explorateur Windows pour vérifier si les fichiers existent
:::
