## Principes de base : Attaque par force brute vs Dictionnaire

SSH (*Secure Shell*) est un protocole de communication chiffré permettant d'administrer un système à distance. L'authentification repose généralement sur un **mot de passe** ou sur une **paire de clés cryptographiques**.

Une attaque par force brute pure consiste à tester toutes les combinaisons de caractères possibles (`aaaa`, `aaab`...), ce qui est trop lent à travers le réseau. En pratique, les attaquants utilisent des **attaques par dictionnaire** : ils soumettent automatiquement des listes de milliers de mots de passe courants ou issus de fuites de données (*wordlists*) à l'aide d'outils spécialisés :

- **Hydra** : Outil de craquage d'authentification réseau en ligne très polyvalent (SSH, FTP, HTTP, RDP...).
- **Medusa** : Craqueur rapide orienté sur le parallélisme massif.
- **Ncrack** : Outil d'audit d'authentification développé par le projet Nmap.

:::tip Ce que voit l'administrateur dans les journaux (Blue Team)
Une attaque par dictionnaire sur SSH est extrêmement bruyante. Chaque tentative échouée génère immédiatement une entrée dans `/var/log/auth.log` :
```text
Failed password for alice from 192.168.220.129 port 49812 ssh2
```
:::

### L'approche inverse : la pulvérisation de mots de passe (*password spraying*)

L'attaque par dictionnaire que vous avez vue vise **un seul compte** et lui soumet des **milliers de mots de passe**. Elle est efficace, mais elle déclenche vite une alarme : des dizaines d'échecs sur `alice` en quelques secondes, c'est un motif facile à repérer (et à bloquer).

Les attaquants utilisent donc souvent la stratégie **opposée**, appelée **pulvérisation de mots de passe** : essayer **un ou deux mots de passe très courants** (`Automne2026!`, `Password123`, `Bienvenue1`…) mais **sur un grand nombre de comptes** :

```bash
# Un seul mot de passe, testé sur TOUS les comptes connus
hydra -L comptes.txt -p 'sexysex' ssh://192.168.220.128
```
- `-L comptes.txt` : une **liste d'utilisateurs** (au lieu de `-l` pour un seul).
- `-p 'sexysex'` : un **seul mot de passe** (au lieu de `-P` pour une liste).

Le pari est statistique : sur 500 employés, il suffit qu'**une seule personne** ait choisi le mot de passe « douteux » pour que l'attaquant entre. Comme il n'y a qu'**un ou deux essais par compte**, l'attaque reste **sous le seuil** des protections qui comptent les échecs *par compte*, et passe souvent inaperçue.

:::note Deux motifs très différents dans `auth.log`
- **Dictionnaire** : beaucoup d'échecs sur **le même** `user` → pic vertical facile à détecter.
- **Pulvérisation** : un échec sur `alice`, un sur `bob`, un sur `charlie`… → bruit **diffus**, bien plus discret.
:::

### Comment se protéger de ces attaques par force brute ?

Aucune mesure n'est suffisante seule : on empile plusieurs couches (*défense en profondeur*).

| Protection | Contre quoi ? | Mise en œuvre |
| --- | --- | --- |
| **Mots de passe forts et uniques** | Dictionnaire **et** pulvérisation | Longueur + complexité, interdiction des mots de passe courants/« de saison » |
| **Bannissement après N échecs** (*Fail2ban*) | Surtout le dictionnaire (échecs concentrés) | Bloque l'**IP** source après X tentatives ratées → **Phase 2** |
| **Limiter les connexions simultanées** (`MaxStartups`) | Ralentit le dictionnaire parallélisé | Option de `sshd_config` |
| **Changer le port par défaut** (22 → 2222) | Réduit le bruit des robots automatiques | `sshd_config` → **Phase 2** |
| **Double authentification (MFA/2FA)** | Dictionnaire **et** pulvérisation | Un mot de passe correct ne suffit plus (code temporaire, clé matérielle) |
| **Clés SSH + désactivation des mots de passe** | **Élimine** la devinette de mot de passe | `PasswordAuthentication no` → **Phase 2** |

:::warning Le point faible de la pulvérisation
Fail2ban, qui bannit après plusieurs échecs **sur une même IP**, reste utile, mais la pulvérisation l'évite en espaçant les tentatives et en changeant d'IP. Les deux vraies parades de fond sont donc : **ne jamais autoriser de mot de passe faible/prévisible** et, idéalement, **supprimer complètement l'authentification par mot de passe au profit des clés SSH** — exactement la démarche de la **Phase 2**.
:::

## 🚩 Phase 1 : CTF Proie-Prédateur (Port 22)

Vous jouez le rôle d'un auditeur de sécurité (*Red Team*) chargé d'évaluer la robustesse des quatre comptes utilisateurs (`alice`, `bob`, `charlie`, `david`) du serveur `192.168.220.128`. **Lancez toutes les commandes depuis le terminal du bureau Kali** (`http://localhost:3000`).

```text
       [Machine Kali : 192.168.220.129]
                     |
       (Hydra / Port standard 22/tcp)
                     v
       [Serveur Proie : 192.168.220.128]
       ├── alice   (🟢 Niveau 1 : Dictionnaire standard)
       ├── bob     (🟡 Niveau 2 : Wordlist spécialisée)
       ├── charlie (🟠 Niveau 3 : Fichier fuité & cadence contrôlée)
       └── david   (🔴 Niveau 4 : Clé privée SSH cachée)
```

### Syntaxe de référence Hydra
```bash
hydra -l [utilisateur] -P [dictionnaire] -t [threads] -f ssh://[adresse_ip]
```
- `-l` : Nom d'utilisateur cible.
- `-P` : Chemin vers le fichier dictionnaire de mots de passe (ex. dans `/usr/share/wordlists/`).
- `-t` : Nombre de connexions parallèles (*threads*).
- `-f` : Arrête l'attaque dès qu'un mot de passe valide est trouvé.

## 🛡️ Phase 2 : Bouclier & Défense

Vous passez maintenant du côté défensif (**Blue Team**). Vous allez sécuriser le serveur en deux grandes parties :
- **Partie A** : Protéger le serveur tout en conservant l'authentification par mot de passe (Mots de passe forts, changement de port et Fail2ban).
- **Partie B** : Éliminer les mots de passe au profit d'une clé cryptographique SSH.

Ouvrez un terminal administrateur (`root`) sur le conteneur Proie, **depuis le terminal de votre hôte** (Mac/PC) :
```bash
docker exec -it ctf-proie bash
```

---

### Partie A : Sécuriser l'authentification par mot de passe

<Tabs>

<TabItem value="etape1" label="1️⃣ Changer les mots de passe">

#### 1. Remplacer les mots de passe compromis et nettoyer les fuites

La première mesure consiste à révoquer les mots de passe présents dans les dictionnaires publics et à supprimer les fichiers sensibles oubliés sur le système.

1. **Supprimer les fichiers compromettants** :
   ```bash
   rm -f /tmp/charlie_candidates.txt
   rm -rf /home/charlie/.backup_david
   ```

2. **Appliquer des mots de passe robustes et complexes** pour `alice`, `bob` et `charlie` :
   ```bash
   echo 'alice:C3g3p_S3cur1t3_2026!A' | chpasswd
   echo 'bob:M0ntr34l_CyB3r_99#B' | chpasswd
   echo 'charlie:K3rb3r0s_Sh13ld_77*C' | chpasswd
   ```
   *(Vous pouvez aussi utiliser `passwd alice` de manière interactive).*

3. **Validation depuis Kali** :
   Relancez votre commande Hydra contre `alice` avec `unix_passwords.txt`. L'outil parcourt toute la liste sans trouver le mot de passe !

</TabItem>

<TabItem value="etape2" label="2️⃣ Changer le port par défaut">

#### 2. Dévier le port SSH standard (`22` ➔ `2222`)

La majorité des robots automatisés sur Internet scannent uniquement le port `22`. Déplacer SSH sur un port non standard (ex. `2222`) élimine plus de 90 % du bruit dans les journaux système.

1. **Modifier `/etc/ssh/sshd_config` sur la Proie** :
   ```bash
   sed -i 's/^#*Port .*/Port 2222/' /etc/ssh/sshd_config
   grep -q "^Port 2222" /etc/ssh/sshd_config || echo "Port 2222" >> /etc/ssh/sshd_config
   ```

2. **Redémarrer le service SSH** :
   ```bash
   service ssh restart
   ```

3. **Validation depuis Kali** :
   - Tentez une connexion sur le port 22 par défaut :
     ```bash
     ssh alice@192.168.220.128
     ```
     *Résultat attendu : `Connection refused`.*
   - Utilisez **Nmap** pour retrouver le nouveau port SSH ouvert :
     ```bash
     nmap -sV -p 22,2222 192.168.220.128
     ```
   - Connectez-vous sur le nouveau port en ajoutant `-p 2222` :
     ```bash
     ssh -p 2222 alice@192.168.220.128
     ```

#### 3. Bannir automatiquement les attaquants avec Fail2ban

Un attaquant qui découvre le port `2222` avec Nmap peut tout de même relancer Hydra en ajoutant `-s 2222`. **Fail2ban** surveille `/var/log/auth.log` et bloque dynamiquement l'adresse IP de l'attaquant via le pare-feu après un nombre défini d'échecs.

1. **Créer la configuration locale `/etc/fail2ban/jail.local`** sur la Proie :
   ```bash
   cat << 'EOF' > /etc/fail2ban/jail.local
   [sshd]
   enabled  = true
   port     = 2222
   logpath  = /var/log/auth.log
   backend  = polling
   maxretry = 3
   findtime = 60
   bantime  = 300
   EOF
   ```
   - `port = 2222` : Surveille notre nouveau port SSH.
   - `maxretry = 3` : Bannissement après 3 échecs.
   - `findtime = 60` : Si les 3 échecs surviennent en moins de 60 secondes.
   - `bantime = 300` : L'adresse IP est bloquée pendant 300 secondes (5 minutes).

2. **Démarrer Fail2ban** :
   ```bash
   activer_fail2ban
   ```

   :::tip Raccourcis fournis par le labo
   La Proie inclut deux commandes pour basculer la défense sans manipuler les services :
   - `activer_fail2ban` → démarre Fail2ban (Phase 2).
   - `desactiver_fail2ban` → arrête Fail2ban **et lève tous les bannissements** (retour en Phase 1).
   :::

3. **Validation depuis Kali (Assaut sur le port 2222)** :
   Lancez Hydra contre le port `2222` (`-s 2222`) :
   ```bash
   hydra -l alice -P /usr/share/metasploit/unix_passwords.txt -s 2222 -t 4 ssh://192.168.220.128
   ```
   Après 3 tentatives, la connexion est bloquée ! Vérifiez l'état de la prison sur la Proie :
   ```bash
   fail2ban-client status sshd
   ```
   **Preuve attendue :** `Currently banned: 1` avec l'adresse IP de votre Kali dans `Banned IP list`.

:::tip Débannir votre machine Kali avant de passer à la Partie B
Pour pouvoir communiquer à nouveau avec le serveur lors de l'étape 4, débannissez l'IP de Kali (`192.168.220.129`) sur la Proie :
```bash
fail2ban-client set sshd unbanip 192.168.220.129
```
Ou, plus simplement, levez tous les bannissements avec le raccourci `desactiver_fail2ban`.
:::

#### 4. Remplacer les mots de passe par une paire de clés SSH

Pour rendre le service SSH insensible à toute forme de devinette de mot de passe (même lente ou distribuée), la meilleure pratique consiste à exiger une **clé SSH** et à désactiver complètement l'authentification par mot de passe.

##### Étape 4.1 : Générer votre paire de clés SSH sur Kali
Dans le terminal de votre machine **Kali**, créez une paire de clés Ed25519 (appuyez sur `Entrée` aux questions pour accepter l'emplacement par défaut `~/.ssh/id_ed25519`) :
```bash
ssh-keygen -t ed25519 -C "etudiant@kali"
```
- `~/.ssh/id_ed25519` : Votre **clé privée** (reste secrète sur Kali).
- `~/.ssh/id_ed25519.pub` : Votre **clé publique** (sera copiée sur le serveur).

##### Étape 4.2 : Copier votre clé publique sur le serveur (port 2222)
Depuis **Kali**, transférez votre clé publique vers le compte `alice` à l'aide de `ssh-copy-id` (entrez une dernière fois le nouveau mot de passe d'Alice défini à l'étape 1 : `C3g3p_S3cur1t3_2026!A`) :
```bash
ssh-copy-id -p 2222 alice@192.168.220.128
```

Testez immédiatement que vous pouvez vous connecter sans mot de passe :
```bash
ssh -p 2222 alice@192.168.220.128
```

##### Étape 4.3 : Désactiver l'authentification par mot de passe sur la Proie
Dans le terminal administrateur du conteneur **Proie**, modifiez `/etc/ssh/sshd_config` pour refuser les mots de passe :
```bash
sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^#*PubkeyAuthentication.*/PubkeyAuthentication yes/' /etc/ssh/sshd_config
service ssh restart
```

##### Étape 4.4 : Validation finale
1. **Connexion légitime par clé depuis Kali** :
   ```bash
   ssh -p 2222 alice@192.168.220.128
   ```
   ✅ Connexion immédiate grâce à votre clé privée `~/.ssh/id_ed25519`.

2. **Test d'attaque Hydra depuis Kali** :
   ```bash
   hydra -l bob -P /usr/share/wordlists/fasttrack.txt -s 2222 ssh://192.168.220.128
   ```
   🛡️ **Résultat :** Hydra s'arrête dès la première seconde car le serveur refuse désormais toute négociation par mot de passe (`Permission denied (publickey)`).
